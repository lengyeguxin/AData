# AData 项目架构设计文档

## 1. 项目概述

AData是一个完整的A股数据采集、存储和可视化系统，旨在为量化分析、策略回测和投资研究提供可靠的数据基础。

### 1.1 设计目标

- **可靠性**：确保数据的准确性和完整性
- **高效性**：优化数据采集和查询性能
- **可维护性**：清晰的代码结构和模块化设计
- **可扩展性**：支持新增数据源和数据类型
- **容错性**：完善的错误处理和断点续传机制

### 1.2 核心特性

- 🔄 **增量采集**：基于游标的断点续传机制
- 📊 **多源支持**：整合Tushare多类API接口
- 🗄️ **高性能存储**：基于DuckDB的列式数据库
- ⏰ **定时更新**：自动化的日/周/月数据更新
- 💾 **双快照架构**：支持高可用和多实例部署
- 📈 **可视化监控**：Streamlit Dashboard实时监控

## 3. 核心组件设计

### 3.1 数据库封装 (Database)

**职责**：提供统一的数据库操作接口，确保线程安全

**关键设计**：
- 线程安全：写操作加锁，保证DuckDB单写模型
- 并发读取：读操作无锁，支持多线程并发
- 连接管理：自动处理连接生命周期

**核心方法**：
```python
class Database:
    def execute(self, query, params=None)      # 执行SQL
    def execute_many(self, query, params_list)  # 批量执行
    def table_exists(self, table_name)          # 检查表存在
    def get_table_count(self, table_name)       # 获取记录数
    def get_table_schema(self, table_name)      # 获取表结构
```

**线程安全策略**：
- 所有SQL操作都通过`write_lock`串行化
- 读操作也加锁（后续可优化为读锁）

### 3.2 API接口封装 (TushareAPI)

**职责**：统一管理Tushare API调用，实现限流和重试

**关键设计**：
- 限流控制：令牌桶算法，避免超限
- 智能重试：指数退避，处理网络抖动
- 代理支持：支持通过代理访问Tushare

**核心方法**：
```python
class TushareAPI:
    def query(self, api_name, **params)     # 查询API
    def _get_token(self)                    # 获取Token
    def _make_request(self, url, data)      # 发起请求
    def _handle_error(self, response)       # 错误处理
```

**限流策略**：
- 每分钟最多500次请求（1万积分）
- 随机休眠1-2秒，避免请求过于集中

### 3.3 数据拉取控制器 (DataFetcher)

**职责**：协调所有数据表的拉取流程，实现优先级和依赖管理

**关键设计**：
- 优先级管理：P0 → P1 → P2 → P3 → P4 五级优先级
- 依赖检查：确保前置表已拉取
- 断点续传：基于游标恢复中断的拉取
- 时间判断：18点后拉取，确保数据完整性

**优先级定义**：
```python
PRIORITY_ORDER = {
    'P0': ['trade_calendar', 'stock_basic', 'index_basic', ...],  # 基础数据
    'P1': ['stock_daily', 'stock_daily_basic', 'index_daily', ...], # 行情数据
    'P2': ['fina_indicator', 'income', 'balancesheet', ...],      # 财务数据
    'P3': ['ths_moneyflow', 'ths_concept_moneyflow', ...],        # 资金流数据
    'P4': ['hots_user', 'hots_trader_detail']                      # 龙虎榜数据
}
```

**拉取流程**：
```
1. 加载交易日历（内存）
2. 按优先级顺序遍历P0 → P4
3. 对每个表：
   a. 检查依赖表是否完成
   b. 读取游标，确定起始位置
   c. 判断是否需要拉取（时间/数据存在性）
   d. 调用collector拉取数据
   e. 更新游标
4. 记录无数据表（跳过后续拉）
```

### 3.4 游标管理器 (GlobalCursorManager)

**职责**：管理数据拉取进度，支持断点续传

**关键设计**：
- 集中存储：所有表的游标存储在`global_cursor`表
- 类型支持：多种游标类型（日期、数值、完成状态）
- 持久化：游标更新实时保存到数据库

**游标类型**：
```python
CURSOR_STRATEGIES = {
    'daily_trade': '交易日期（YYYYMMDD）',
    'daily_natural': '自然日期（YYYYMMDD）',
    'yearly': '年份（YYYY）',
    'none': '无游标（全量拉取）',
    'special_ths_member': '同花顺概念股'
}
```

**核心方法**：
```python
class GlobalCursorManager:
    def get_cursor(self, table_name)           # 获取游标
    def update_cursor(self, table_name, value) # 更新游标
    def is_completed(self, table_name)         # 检查是否完成
    def initialize(self)                       # 初始化游标表
```

### 3.5 采集器基类 (BaseCollector)

**职责**：提供通用的数据采集逻辑，消除代码冗余

**关键设计**：
- 模板方法：定义拉取流程，子类实现细节
- 数据转换：统一的日期格式转换
- 批量插入：优化写入性能

**采集流程**：
```python
def collect(self, **params):
    1. 调用API获取数据
    2. 数据转换（日期格式、类型转换）
    3. 构建INSERT语句
    4. 批量插入数据库
    5. 返回记录数
```

**子类实现**：
- `_extract_values()`: 提取字段值
- `_build_insert_query()`: 构建INSERT语句

### 3.6 定时任务调度器 (DataScheduler)

**职责**：管理定时任务，实现自动化数据更新

**关键设计**：
- 多任务调度：支持多个定时任务同时运行
- 错误处理：任务失败不影响调度器运行
- 状态查询：提供任务状态查询接口

**定时任务**：
```python
任务列表：
1. 日线数据拉取：每天18:00
2. 快照生成：每30分钟
3. （可扩展）周线更新：每周五19:00
4. （可扩展）月线更新：每月20:00
```

**核心方法**：
```python
class DataScheduler:
    def start()                          # 启动调度器
    def stop()                           # 停止调度器
    def add_daily_fetch_job()           # 添加日线拉取任务
    def add_snapshot_job()              # 添加快照任务
    def get_jobs_status()               # 获取任务状态
```

### 4.2 断点续传机制

**原理**：每个表维护一个游标，记录最后拉取的位置

**实现**：
1. 开始拉取前，读取游标表
2. 从游标位置继续拉取
3. 每次拉取成功后更新游标
4. 中断后重新启动，从游标位置继续

**示例**：
```
stock_daily表：
  游标: 20260409
  → 下次拉取从 20260410 开始

income表：
  游标: 20260409
  → 下次拉取 ann_date > 20260409
```

### 4.3 双快照架构

**目的**：支持高可用和多Dashboard实例

**设计**：
```
主数据库（写入）：
  └─ database/adata.db

快照数据库（只读）：
  ├─ database/adata_snapshot.db       # AData项目
  └─ /path/to/AIStock/adata_snapshot.db  # AIStock项目

同步机制：
  定时任务每30分钟复制主数据库到快照位置
```

**优势**：
- Dashboard读取快照，不影响主数据库写入
- 支持多个Dashboard实例同时运行
- 快照损坏不影响主数据库

## 7. 错误处理

### 7.1 错误分类

| 错误类型 | 处理策略 |
|----------|----------|
| 网络超时 | 重试（最多2次） |
| API限流 | 等待60秒后重试 |
| 数据格式错误 | 记录日志，跳过 |
| 数据库写入错误 | 回滚事务，记录日志 |
| 配置错误 | 启动失败，提示用户 |

### 7.2 重试机制

```python
重试策略：
1. 第一次失败：等待60秒重试
2. 第二次失败：记录日志，标记失败
3. 3次以上失败：跳过该表，继续下一个
```
